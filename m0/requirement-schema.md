# V0 Requirement Schema

> 本文件是"需求采访"环节的结构化模板。
> 它不是给用户填的问卷，而是 **Interview Agent 的内部对照表**：用它检查"用户自由表达里已经说了什么、还缺什么、缺的东西会不会改变项目方向"。
>
> 设计原则：
> 1. **每个字段都必须自证价值**——"如果这个字段缺失，会改变哪个决策？"答不上来的字段，V0 不保留。
> 2. **状态三分**：`complete`（已明确）/ `partial`（说了一半、有歧义）/ `missing`（没提）。
> 3. **追问优先级三分**：
>    - **P0 · 必问**：缺失会直接改变项目目标 / 范围 / 关键技术决策。
>    - **P1 · 可问**：缺失会降低质量，但不会改变大方向。
>    - **P2 · 留给 Agent**：属于实现细节，按 C 模式由 Coding Agent 自主决定，不打扰用户。
> 4. V0 只采集到"足够让 Coding Agent 不猜关键业务意图"即可，不追求 100% 完整。

---

## 0. Project（项目身份）

| 字段 | 含义 | 状态 | 影响决策（缺失会怎样） | 优先级 |
|---|---|---|---|---|
| `name` | 项目名称/代号 | `____` | 影响 Prompt 称呼与产物命名，不改变方向 | P2 |
| `one_liner` | 一句话描述它是什么 | `____` | **缺失则无法对齐"我们在做什么"**，是最高频的歧义源 | P0 |
| `original_intent` | 用户自由表达的原文（逐字保留） | `____` | 是后续 S3 确认与最终 Conformance 对照的"原始 Intent"基线，**必须原样保留，不得改写** | P0 |

> `original_intent` 不做润色、不总结、不缩写。它是"最终回到原始意图"的对照物。

## 1. Goal（为什么做）

| 字段 | 含义 | 状态 | 影响决策 | 优先级 |
|---|---|---|---|---|
| `why` | 动机/背景：为什么现在要做这个 | `____` | 缺失则分不清"真想解决的问题"和"顺手想加的功能" | P0 |
| `problem` | 想解决的核心问题是什么 | `____` | 缺失则范围无法界定，功能清单会失控 | P0 |
| `success_snapshot` | 成功后是什么画面（谁、在什么场景、得到什么） | `____` | 缺失则验收标准失去锚点，容易做成"作者觉得对"的东西 | P0 |

---

## 2. Users（为谁做）

| 字段 | 含义 | 状态 | 影响决策 | 优先级 |
|---|---|---|---|---|
| `who` | 谁是使用者 | `____` | 缺失则优先级排序无依据 | P0 |
| `scenarios` | 在什么场景下用 | `____` | 缺失则分不清核心路径和边角 case | P1 |
| `assumptions` | 对用户/环境的假设（必须显式列出并标注"待验证"） | `____` | 假设藏着会导致 Agent 按错误前提开发 | P1 |

---

## 3. Requirements（做什么 / 不做什么）

| 字段 | 含义 | 状态 | 影响决策 | 优先级 |
|---|---|---|---|---|
| `core_features` | 核心功能（MVP 必须有，P0） | `____` | **缺失则没有 MVP 边界，Agent 会无限加功能** | P0 |
| `secondary_features` | 次要功能（有更好，P1） | `____` | 影响排期，不影响能否跑通 | P1 |
| `non_goals` | **明确不做什么（范围边界）** | `____` | 缺失则 Scope Drift 无刹车——长任务最容易失控的地方 | P0 |

> `non_goals` 与 `core_features` 同等重要。规划文档第十九节"人决定边界"在这里落地。
>
> **"全部 / 所有 / 完整"类表述必须枚举化**（Revit 第二例的真实教训）：用户说"所有构件/全部数据/整个项目"时，必须追问出**可枚举的范围清单**（哪些类别/类型在范围内），并同步确认**自检分母**——"无遗漏/全绿"是对什么口径说的？没有枚举清单和分母口径，自检只能证明"清单内无遗漏"，清单外的内容会**静默消失**（Agent 与用户都以为覆盖了，且任何自检都发现不了）。

## 3b. Inputs（输入素材 / 数据，仅当项目接收外部输入时）

如果这个工具/产品要接收用户或外部的数据、文件、模型，这一节必填。

| 字段 | 含义 | 状态 | 影响决策 | 优先级 |
|---|---|---|---|---|
| `input_source` | 项目需要什么输入？从哪来？（如用户导出的 glTF、上传的表格、接的 API） | `____` | **缺失则不知道产物要吃什么，技术方案无从谈起** | P0（有输入时） |
| `input_path` | 该输入在目标环境能否直接获取/解析？是否需要转换步骤？ | `____` | **用户说"工具负责把 X 导进来"时必问：X 是专有格式时，纯前端/单文件往往读不了** | P0（有专有格式时） |
| `input_toolchain` | 输入由什么工具链产生（导出器/插件及版本、格式变体如 Draco 压缩/量化、单位制） | `____` | 缺失则"能否解析"只验证到格式名——同名格式的压缩变体/单位差异会让下游解析失败或尺寸全错 | P0（有外部输入时） |
| `input_size` | 输入量级/规模（模型大小、数据量、条数） | `____` | 缺失则无法判断性能/轻量化需求 | P1 |

> **触发规则**：当用户提到"导入 / 读取 / 上传某文件格式"时，必须主动问 `input_path`——
> 典型陷阱是"工具要负责读 .rvt / .psd 等专有格式"，而纯前端单 HTML 根本读不了，中间必须有一步转换。
> 同时确认 `input_toolchain`：**格式名相同 ≠ 能解析**（如同为 glTF，Draco 压缩变体、单位制不同，解析结果完全不同）。

## 4. Constraints（硬约束 · Hard）

这些是 Coding Agent 不能违反的：

| 字段 | 含义 | 状态 | 影响决策 | 优先级 |
|---|---|---|---|---|
| `time` | 时间/周期期望 | `____` | 影响 MVP 取舍与是否接受技术债 | P1 |
| `cost` | 成本/预算（如 API、第三方、服务器） | `____` | 缺失则可能选中用户付不起的方案 | P1 |
| `tech_limit` | 技术限制：必须/禁止的语言、框架、版本、平台 | `____` | **用户点名的技术栈是硬约束，不能由 Agent 替换** | P0 |
| `env_limit` | 运行/部署环境（操作系统、浏览器、网络限制等） | `____` | 缺失则产物跑不起来 | P1 |
| `compliance` | 安全/合规/隐私/授权要求 | `____` | 红线，缺失可能导致违法或不可用 | P0（有则必问） |

---

## 5. Preferences（软约束 · Soft，可被 Agent 优化）

| 字段 | 含义 | 状态 | 影响决策 | 优先级 |
|---|---|---|---|---|
| `preferred_tech` | 用户指定的偏好技术（注意与 `tech_limit` 区别：可商量） | `____` | 影响初始技术选型建议 | P1 |
| `preferred_style` | 偏好的实现/交互风格（简洁 vs 完整等） | `____` | 影响代码组织与文档详略 | P2 |

> 与 `tech_limit` 的区别：`tech_limit` 是"必须/禁止"，违反即错；`preferred_tech` 是"倾向"，Agent 有正当理由可以偏离，但要说明。

---

## 6. Success Criteria（怎么算完成）

| 字段 | 含义 | 状态 | 影响决策 | 优先级 |
|---|---|---|---|---|
| `done_definition` | 什么算"这个项目做完了" | `____` | **缺失则 Agent 会自我宣布完成，"完成"失去客观标准** | P0 |
| `acceptance` | 可操作的验收方式（点哪里/跑什么/看什么结果） | `____` | 缺失则"完成"无法被验证，只能靠 Agent 自说自话 | P0 |
| `reference_anchor` | 验收对照物：参考网站/产品/截图/原型的链接或名字 | `____` | 用户说"像/接近/参考 XX"而 XX 不具体，则验收退化为"作者觉得像"，无法对照（BIM 第一轮的真实教训） | P0（用户提过参考时必问） |

> 这两个字段合起来回答：**别人怎么知道它真的成了？**（"说做完了"≠"验证通过"）

---

## 7. 预留字段（V0 可空，V1 填实）

规划文档第二十七节的 11 项模型中，V0 先把占位留好，避免以后改 Schema 结构：

| 字段 | 含义 | V0 处理 |
|---|---|---|
| `decision_boundary` | 什么决策必须回来问人、什么 Agent 可自主 | V0 用默认值（见下），不单独采访 |
| `verification` | 由谁/用什么验证完成 | 并入 Part A，见模板 |
| `recovery` | 卡住/失败时怎么办 | 并入 Part A，见模板 |
| `dynamic_state_hint` | 未来 STATE.md 的位置提示 | 已落地为 `templates/progress.md`（PROGRESS.md，编译时随包交付） |

### V0 默认 decision_boundary（除非用户另行指定）

- **必须回来问人（Hard）**：改变 `goal` / `non_goals`、违反 `tech_limit`/`compliance`、需要新花钱/装东西、删除用户已确认要的东西。
- **Agent 可自主（Soft）**：文件组织、库的具体选择（未被点名时）、内部实现、错误处理细节、命名、文档措辞。

---

## 8. 完成度自检（S2 → S3 的 Gate）

Interview Agent 在进入 S3 前，必须逐项过：

- [ ] 所有 P0 字段状态是否都已 ≥ `partial`？（任何一个 P0 仍 `missing`，回到 S2 追问）
- [ ] `non_goals` 是否明确？（哪怕写"暂无明确排除项"也要显式记录）
- [ ] `original_intent` 是否逐字保留？
- [ ] 是否存在"用户说了一半、Agent 自行脑补补全"的字段？（有则标 `partial`，必要时追问）
- [ ] P1/P2 字段里，有没有其实属于 P0 的？（防止漏问关键问题）
- [ ] 项目若接收外部输入，`input_source` / `input_path` 是否清楚？用户说要导入某专有格式时，是否已追问"能否直接解析 / 是否需要转换"？
- [ ] 有外部输入时，产生输入的工具链是否已确认（导出器/压缩变体/单位制）？
- [ ] 用户是否用"像 / 参考 / 接近 XX"表达过期望？XX 是否已具体化为可对照的参考物（网址/截图/名字）？
- [ ] 需求里的"全部 / 所有 / 完整"类表述是否已枚举化为可对账的清单？验收/自检的分母口径是否已确认（全绿 = 分母内对平 + 分母外如实披露）？

> 这张清单是"需求的单元测试"：在进入下一阶段前必须全绿。
