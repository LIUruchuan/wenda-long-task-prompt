# V0 State Machine

> 把流程状态显式建模，而不是依赖聊天历史。
> 任何时刻，Agent 都应能回答：**现在在哪个状态？下一步是什么？什么条件才能离开？**

---

## 状态总览

```
S0_INIT
  ↓
S1_FREE_EXPRESSION
  ↓
S2_DISCOVERY  ←───┐
  ↓               │
S2b_FOLLOWUP ─────┘
  ↓
S3_CONFIRMATION ── Gate 1（需求确认）
  ↓ 确认
S4_PLANNING
  ↓
S4b_PLAN_REVIEW ── Gate 2（计划确认）
  ↓ 确认
S5_COMPILATION
  ↓
S6_FINAL_OUTPUT
```

两个 **Human Gate**：S3（"我理解对了吗？"）、S4b（"计划可以吗？"）。未过 Gate 不得向下。

---

## S0 — INIT

- **进入**：用户启动一个新的需求初始化任务（或说"开始需求采访/帮我规划个项目"）。
- **Agent 行为**：自我介绍能力边界——"我会先听你讲，再帮你把项目整理成 Coding Agent 能用的初始化上下文"。不立刻给方案。
- **输出**：空的 `requirement_state`，`raw_user_intent` 待填。
- **迁移**：有用户输入 → S1。

## S1 — FREE_EXPRESSION（自由表达）

- **进入**：S0，或用户开始补充想法。
- **Agent 行为（纪律）**：
  - 不急着套模板、不急着问"你的用户是谁"。
  - **不打断、不给技术方案、不纠正**。
  - 先把用户说的接住，复述一句"我听到你想做……"，让他知道被理解了。
  - 允许用户连续、零散、跳跃地补充。
- **退出条件（启发式，不是硬规则）**：
  - 用户主动停下来（"大概就是这样/我说完了"），或
  - 用户连续两轮没有新信息，且 Agent 判断"已收集到可对照 Schema 的素材"。
- **输出**：
  ```json
  {
    "raw_idea": "用户原文",
    "user_goals": ["……"],
    "mentioned_features": ["……"],
    "mentioned_constraints": ["……"]
  }
  ```
- **迁移**：素材够做一次 Schema 对照 → S2。

## S2 — DISCOVERY（模板检查）

- **进入**：S1 结束。
- **Agent 行为**：把 `raw_user_intent` 逐条对照 `requirement-schema.md`，给每个字段打状态（complete/partial/missing），并按 P0/P1/P2 分级。
- **输出**：`requirement_state`（一张覆盖度表）+ 判断"哪些缺失会改变项目方向"。
- **迁移**：
  - 还有 P0 缺失或 `partial` 影响判断 → S2b。
  - 全部 P0 ≥ partial、通过 Schema 第 8 节自检 → S3。

## S2b — FOLLOWUP（追问）

- **进入**：S2 发现需要补的信息。
- **Agent 行为（纪律）**：
  - **一次只问最关键的少数问题**（建议 ≤3 个），不要发问卷。
  - 只问 P0；P1 攒到用户自然聊到时再带；P2 不问。
  - 每个问题都要能回答"为什么问这个"——如果答不上来，就别问。
  - 问法是开放式的，不要诱导用户选你心里的答案。
- **输出**：用户回答 → 回填 `requirement_state` → 回到 S2 重新对照。

## S3 — CONFIRMATION（需求确认 · Gate 1）

- **进入**：S2 自检全绿。
- **Agent 行为**：把当前理解整理成一段人能读的话：
  > 我理解你的项目是：……（目标/用户/核心功能/明确不做/约束/成功标准）。
- **输出**：需求摘要 + 一个问题——"这是对项目需求的正确理解吗？可以补充或修改。"
- **迁移**：
  - 用户说"不对/改这里" → 回到 S2（只针对改动的部分）。
  - 用户确认 OK → S4。
- **纪律**：不要在这里问技术实现问题；确认的是"需求"，不是"怎么做"。

## S4 — PLANNING（规划）

- **进入**：Gate 1 通过。
- **Agent 行为**：按 `prompts/planning-prompt.md` 执行。只规划"方向"，不写代码、不把实现钉死。
- **输出**：`project_plan`（整体方向 / MVP 划分 / 技术路线倾向 / 主要模块 / 开发顺序 / 风险 / 验收策略）。
- **迁移**：草稿产出 → S4b。

## S4b — PLAN_REVIEW（计划确认 · Gate 2）

- **进入**：S4 草稿完成。
- **Agent 行为**：把计划交给用户看，明确标出"这里是我建议、你可以否掉"的点，尤其是技术路线和阶段划分。
- **迁移**：
  - 用户要求调整 → 回 S4。
  - 用户确认 → S5。

## S5 — COMPILATION（编译）

- **进入**：Gate 2 通过。
- **Agent 行为**：按 `compiler.md` 把"需求 + 决策 + 计划 + 工程规则"组装成两部分：
  - Part A · Engineering Instructions（怎么工作）
  - Part B · Project Context（做什么/不做什么）
- **纪律**：不是把对话记录拼成长 Prompt；按模板结构化组装。
- **输出**：`engineering-instructions.md` + `project-context.md` + `final-prompt.md`（内联两部分全文）+ `PROGRESS.md`（从模板初始化）。
- **迁移**：→ S6。

## S6 — FINAL_OUTPUT（交付）

- **进入**：S5 完成。
- **Agent 行为**：把最终 Context 交给用户，并用一句话说明"下游 Coding Agent 怎么用它"。
- **输出**：交付文件 + 使用说明。
- **收尾动作**：回读一遍 `original_intent`，检查最终 Context 有没有跑偏到用户没说过的方向；有则指出并回 S3/S5。

---

## 通用规则

1. **状态只允许向下推进，回退必须显式**：任何"回退"都要说明回到哪个状态、为什么。
2. **用户随时可喊停**："先别规划"→ 回到当前阶段；"这个方向不对"→ 回 S3。
3. **不在错误状态做错误的事**：
   - S1/S2 阶段不聊技术实现。
   - S3 阶段不做规划。
   - S4/S5 阶段不再翻需求（除非用户主动提出）。
4. **每次状态切换，用一句话告诉用户**"我们进入到下一步了：……"，保持透明。
