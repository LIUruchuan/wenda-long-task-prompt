# 可访问性检查表（Accessibility Checklist）

> references/ · 按需加载：产物是**面向人的界面**（网页、桌面 UI、移动界面、图表/可视化）时启用。
> 用法：编译时勾选"可访问性"领域 → 随包交付；核心红线内联 Part A §3b。

---

## 适用信号

- Web 页面 / 单 HTML / 桌面应用 / 任何有人操作的界面
- 有颜色、对比度、交互、表单、弹窗、拖拽等 UI 元素
- 用户说"给客户/评审演示""公开使用"（受众越广，可访问性越重要）

## 核心检查项

- [ ] 所有功能可**键盘操作**完成（Tab 焦点可见、无键盘陷阱、无纯拖拽必选项）
- [ ] 颜色不是唯一信息载体（红/绿状态同时有文字/图标/形状）
- [ ] 文本对比度满足基本可读（正文与背景对比明显，不依赖纯低对比设计）
- [ ] 图片/图标有替代文本（alt / aria-label）；非装饰性内容不静默
- [ ] 表单有 label；错误提示不只靠颜色，且有明确位置
- [ ] 动画/自动播放可暂停或可关闭（尊重用户偏好）
- [ ] 弹窗/模态：可关闭、焦点不困在里面、有遮罩语义

## 常见陷阱

- "视觉好看"与"可读"冲突时默认选择好看，未考虑色弱/低视力用户
- 只测鼠标操作，键盘与读屏路径从未验证
- 把可访问性当成"加分项"而非"基本可用性"
- 用颜色区分状态（如红绿开关），色弱用户无法区分

## 反合理化表

| 借口 | 现实 |
|---|---|
| "目标用户都能看见" | 你无法确认；键盘用户/色弱用户/低视力用户都是真实使用群体 |
| "加 alt 很麻烦" | 一行字段，几秒钟，却是无图/读屏用户的全部信息 |
| "这是演示工具，不重要" | 演示场景恰好在评审屏上，可读性直接影响评估 |

## Red Flags（出现即停）

- UI 产物没有任何键盘路径说明或验证
- 验收标准不包含"键盘可操作/颜色不唯一"类条目
- 出现"装饰性图片不设替代文本"的决定且未说明

## 验证方式

- 键盘走查：只用 Tab/Enter/Space/方向键完整走一遍主流程
- 色弱视角：对关键状态（错误/成功/选中）用灰度或色弱模拟检查是否仍可区分
- 记录在 PROGRESS §4：走查路径 + 结果
