# API / 接口设计检查表（API & Interface Design Checklist）

> references/ · 按需加载：产物含**对外接口**——HTTP API、库/模块的公开函数、文件格式契约、插件接口、数据交换协议时启用。
> 用法：编译时勾选"API/接口设计"领域 → 随包交付；核心红线内联 Part A §3b。

---

## 适用信号

- 有 HTTP 端点、RPC、WebSocket 消息、命令行参数
- 有对外公开的函数/类/模块（被其他代码调用）
- 有自定义文件格式 / JSON 结构 / 数据交换协议
- 产物会被**第二个消费者**使用（另一模块、另一程序、AI 模型）

## 核心检查项

- [ ] 接口契约**先定义后实现**：字段名、类型、单位、必填/可选、错误语义写清楚（契约优先）
- [ ] 错误处理显式：错误码/错误信息可区分"参数错/不存在/服务器错"，不吞错误
- [ ] 版本意识：接口变更是否破坏既有消费者；破坏性变更是否显式声明
- [ ] 数据语义钉死：单位（米/毫米）、坐标参照系、时间格式、编码——与 wenda 的"坐标语义约定"同级
- [ ] 空值/缺字段/类型不对的输入有明确行为（拒绝 or 默认值，不能静默出错）
- [ ] 兼容性：向后兼容考虑（新增字段默认值、旧字段保留）
- [ ] 格式自解释：有元信息（版本、单位、生成工具），便于对账与调试

## 常见陷阱

- 格式名相同但语义不同（同为 JSON，字段单位/参照系不同——revit 例的"格式名相同≠能解析"）
- 接口只在"输入合法"路径测过，错误路径无定义
- 字段命名/结构随实现演进，没有一份稳定的契约文档
- 隐式约定（"调用方自己知道传毫米"）而非显式写入

## 反合理化表

| 借口 | 现实 |
|---|---|
| "就我一个人用，不用写契约" | 三个月后的你和一个陌生人没区别；AI 消费者更依赖显式契约 |
| "字段名一看就懂" | "一看就懂"不等于语义钉死（单位/参照系/边界全靠猜） |
| "先实现后补文档" | 后补的文档描述的是"实现做了什么"，不是"接口承诺什么" |

## Red Flags（出现即停）

- 接口字段的单位/参照系/可选性未写进任何交付物
- 错误路径（缺字段、坏数据、异常输入）无定义行为
- 接口变更没有在 PROGRESS 决策记录里写明"破坏了什么"

## 验证方式

- 用**契约测试**：按契约字段逐个构造合法/非法输入，核对行为与契约一致
- 与消费者联测：把数据交给真实下游（另一模块/AI）验证能否理解
- 契约文档本身随包交付，成为对账基准
