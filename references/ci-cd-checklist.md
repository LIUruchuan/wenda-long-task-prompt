# CI / CD 检查表（CI/CD Checklist）

> references/ · 按需加载：产物需要**自动化构建/测试/发布**、有多步验证流水线、或"跑通什么才算过"需要被固定下来时启用。
> 用法：编译时勾选"CI/CD"领域 → 随包交付；核心红线内联 Part A §3b 质量门槛。

---

## 适用信号

- 产物有构建/编译/打包步骤
- 有可重复的检查命令（lint、test、build、验证脚本）
- 用户期望"每次改动后按固定流程验证"而非每次临时想命令

## 核心检查项

- [ ] 把"如何验证才算过"写成**可重复的命令序列**（安装→构建→检查→测试→运行验证），随包交付
- [ ] 每个命令标注：在哪运行（本地 / 特定环境）、跑什么范围、通过标准（退出码/输出）
- [ ] 验证环境与产物运行环境一致或写明差异（如"编译在 VS 完成，加载验证必须在真实 Revit"）
- [ ] 快速检查与全量检查分层：改动后跑快的，交付前跑全的
- [ ] 门禁定义清楚：哪些失败**阻断**（必须修复）、哪些只是提示
- [ ] 无环境依赖的验证优先（能用命令/文件的不用 GUI 人工目测）

## 常见陷阱

- 验证命令存在于 Agent 记忆里而不在任何文件里（换会话即丢）
- "编译通过"当"验证通过"（revit 例：编译 ≠ 在真实环境运行）
- 门禁全是人工目测，无人记得"上次怎么验的"
- 命令因环境漂移（版本、路径）而不可复现

## 反合理化表

| 借口 | 现实 |
|---|---|
| "命令我记着，不用写下来" | 长任务跨会话，记忆不可靠；文件才可靠 |
| "编译过了就是好了" | 编译只证明语法与类型，不证明行为正确 |
| "每次验证方式差不多" | "差不多"就是不可复现，门禁会悄悄漂移 |

## Red Flags（出现即停）

- 交付物中找不到任何"可运行验证命令"
- 验证步骤依赖 Agent 的记忆而非文件
- "通过"的定义含糊（没写跑什么、看什么输出）

## 验证方式

- 新会话/新环境按文档命令序列**完整重跑一遍**，确认可复现（dogfood 即此类验证）
- 在 PROGRESS §4 记录每次验证的**实际命令 + 输出摘要**，而非只写"通过"
