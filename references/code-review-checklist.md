# 代码评审清单（Code Review Checklist）

> references/ · 共享清单：任何由 Agent 产出的**代码/脚本/数据逻辑**都建议启用（与"调试"领域配套）。
> 用法：编译时勾选"评审"或任一运行类领域 → 随包交付；Part A §9 评审纪律引用。

---

## 评审五轴

| 轴 | 问什么 |
|---|---|
| 正确性 | 是否符合规格/需求？边界与错误路径处理了吗？测试测的是对的东西吗？ |
| 可读性 | 名字清楚吗？逻辑直白吗？有没有为了"聪明"牺牲可懂？ |
| 架构 | 符合既有模式吗？职责边界清楚吗？抽象值得它的复杂度吗？ |
| 安全 | 外部输入在边界验证了吗？密钥/注入/XSS 有吗？（见 security-checklist） |
| 性能 | 有 N+1/无界循环/大对象进热路径吗？（见 performance-checklist） |

## 分级前缀（评审意见必带级别）

| 前缀 | 含义 | 作者动作 |
|---|---|---|
| **Critical** | 阻断交付：数据丢失、安全漏洞、功能破坏 | 必须修复 |
| **Required** | 应修复 | 必须处理（或显式说明理由搁置） |
| **Nit / Optional** | 可选建议 | 可不改 |
| **FYI** | 背景信息 | 无需动作 |

## 评审协议（两段式）

1. **任务级评审**：每个可独立验证的增量完成后，用五轴过一遍该增量（自查或独立复核）。
2. **收尾级评审**：全部完成、宣布"完成"前，对整体过一遍（对照 Part B 验收 + 五轴 + 已知缺口）。
3. 环境支持子代理时：实现者与评审者**分离**（不同上下文/模型），评审者只看增量与规格；否则至少做**独立复核**（隔一段时间/换视角重读）并在 PROGRESS 留痕。
4. 同一问题修复 3 轮仍未解决 → 停止自行尝试，按 Part A §2 问人（附已试路径与建议）。

## 反合理化表

| 借口 | 现实 |
|---|---|
| "我写的我清楚" | 作者看不见自己的假设盲区；第二双眼睛是评审的全部意义 |
| "测试过了就是好的" | 测试证明行为，不证明架构/安全/可读性 |
| "评审太慢" | 不评审的代价是 bug 进交付、返工更贵（revit 例 4 个 P1 bug） |
| "AI 生成的代码应该没问题" | AI 代码更自信地错，更需要评审而非更少 |

## Red Flags（出现即停）

- 增量/交付前无任何评审动作或留痕
- 评审意见无分级，作者分不清哪些必须改
- "LGTM"式评审（无证据的放行）
- 实现者自己给自己评审且无独立视角

## 验证方式

- 评审记录：每轮评审的轴、发现、处置（修复/搁置+理由）写入 PROGRESS §4/§5
- 抽查：任取一个已"完成"的增量，能在 PROGRESS 找到其评审留痕
