# 调试指南（Debugging Guide）

> references/ · 按需加载：任何**会运行、会出错**的产物都适用；尤其是"卡住/报错/结果不对"类任务。
> 用法：编译时勾选"调试"领域 → 随包交付；Part A §5 失败与恢复引用本指南。

---

## 适用信号

- 产物有运行逻辑（代码、脚本、数据管道、插件）
- 用户预期任务中会出现"报错/卡住/结果不对"并需要自主排障
- 长任务期间 Agent 需要自己定位问题而非直接问人

## 核心检查项

- [ ] 先**复现**再修：构造能稳定复现问题的输入/步骤，不修"偶尔出现"的幽灵
- [ ] **根因定位**：区分症状与根因（报错信息只是症状，沿调用链/数据流向上游追根因）
- [ ] 二分定位：多环节出错时，从中间点切分验证，一次缩小一半范围
- [ ] 用证据判断而非猜测：每个"我觉得是 X 的问题"先加验证（打印/日志/最小复现）再动手
- [ ] 修复后**回归验证原症状消失**，且相邻功能未破坏
- [ ] 修不好的问题：停止硬试，回 Part A §2 判断是否该问人（附上已试路径）

## 常见陷阱

- 修症状不修根因（换了报错文案但数据仍错）
- 反复随机尝试（改一行试一次），不做系统性二分
- 忽略环境差异（版本/路径/编码/时区）——"我这能跑"≠"目标环境能跑"
- 用"可能是/应该是"代替实测验证

## 反合理化表

| 借口 | 现实 |
|---|---|
| "多试几次总能好" | 随机尝试没有信息增益，烧轮次且可能引入新问题 |
| "报错信息说明白了" | 报错是症状；根因在调用链/数据流的更上游 |
| "这个错误是环境问题" | 环境问题也是问题：钉死版本/路径/编码，让它可复现 |

## Red Flags（出现即停）

- 同一问题尝试多次而无任何根因分析记录
- 修复时改了报告的错误但没验证原症状消失
- "应该是环境问题"但未确认目标环境的实际配置

## 验证方式

- 最小复现：把问题缩小到最小输入/最少步骤，记录在 PROGRESS §5
- 修复证明：修复前后各跑一次复现步骤（证据留 PROGRESS §4）
- 根因记录：PROGRESS §3 决策记录写明"为什么放弃某路线/根因是什么"，防止绕回
