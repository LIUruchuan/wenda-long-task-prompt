# 依赖与迁移检查表（Dependency & Migration Checklist）

> references/ · 按需加载：项目会**引入第三方依赖**、**升级库/框架/平台版本**、**弃用旧组件/迁移数据**时启用。
> 用法：编译时勾选"依赖与迁移"领域 → 随包交付；核心红线内联 Part A §3b。

---

## 适用信号

- 产物依赖第三方库、CDN、插件、运行时
- 任务包含版本升级（库/框架/Revit 版本/语言版本）
- 任务包含数据迁移、格式转换、组件替换（旧→新）

## 核心检查项

- [ ] **引入每个依赖前五问**：现有栈能否解决？体积/复杂度多大？是否活跃维护？有无已知漏洞？许可证是否兼容？
- [ ] 依赖升级视作**行为变更**而非"顺手 bump"：读变更日志，不只读版本号
- [ ] 一次只升级一个依赖（或强相关小组），出问题能定位到是谁
- [ ] 迁移/替换有**往返或对照验证**：旧→新→旧能否往返；迁移前后数据可对照（revit 例的往返逐字段对照）
- [ ] 迁移有回滚路径或备份：失败时可回到迁移前状态
- [ ] 版本钉死：锁文件/明确版本号，不靠"最新版"（环境漂移源）
- [ ] 弃用/替换旧组件时，确认无残留调用（死代码清理）

## 常见陷阱

- "顺手加个库"不做五问——每个依赖都是长期负债
- 一次升级一堆依赖，坏了不知道是哪个
- 迁移只验证"能跑"，不验证"数据/行为等价"
- 依赖锁定用"latest"，两天后环境漂移全部失效

## 反合理化表

| 借口 | 现实 |
|---|---|
| "这个库很小，没风险" | 传递依赖可能拉进几十个间接包，每个都是攻击面 |
| "升级顺便一起做了" | 批量升级把"哪个包导致挂"藏起来，回滚也变得不可能 |
| "迁移后能运行就算成功" | 能运行 ≠ 行为等价；数据对照才是迁移验收 |
| "用最新版不会有错" | 最新版是未知数；版本钉死才可复现 |

## Red Flags（出现即停）

- 新增依赖无"为什么用它、替代方案是什么"记录
- 版本升级无变更日志核对、无前后验证
- 迁移无往返/对照验证、无回滚路径
- 锁文件/版本号未固定

## 验证方式

- 依赖引入前后各跑一遍关键验证（新增依赖不破坏既有行为）
- 升级验证：升级前全绿 → 升级后全绿 → 变更日志与行为差异已核对
- 迁移验证：逐字段/逐条对照迁移前后数据（PROGRESS §4 留证据）
