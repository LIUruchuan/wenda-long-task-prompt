# 可观测性检查表（Observability Checklist）

> references/ · 按需加载：产物会**长时间运行 / 自主执行 / 出错后需要复盘**时启用（长任务项目普遍适用）。
> 用法：编译时勾选"可观测性"领域 → 随包交付；核心红线内联 Part A §3b 与 PROGRESS §4。

---

## 适用信号

- 长任务自主执行（Agent 跑很久，中间无人看）
- 产物有运行日志、执行过程、转换过程（数据管道、批量处理、后台任务）
- 出错后需要复盘"当时发生了什么"

## 核心检查项

- [ ] 关键步骤**留痕**：做了什么、输入什么、输出什么、成败——落到 PROGRESS/日志，不只在对话里
- [ ] 证据可追溯：每个"完成"声明指向可复现的证据（命令输出、文件、截图、可复现步骤）
- [ ] 中间产物可检查：关键转换留出中间文件/摘要（如导出 JSON、计数报告），便于对账
- [ ] 错误不静默：失败有记录（原因 + 现场），不是"看起来没发生"
- [ ] 决策有记录：为什么选 A 不选 B（PROGRESS §3），事后可复盘
- [ ] 规模/进度可见：批量任务有进度标记（处理到哪、剩余多少）

## 常见陷阱

- 状态只存在于对话记忆，会话中断即丢失
- "完成了"但没有任何证据可以复查（revit 例：自检全绿却无清单外证据）
- 决策没有记录，后续绕回去重试失败路线（PROGRESS §3 的用途）
- 错误被吞掉（catch 空实现），故障无声发生

## 反合理化表

| 借口 | 现实 |
|---|---|
| "我记录在心里了" | 长任务记忆不可靠，文件才是唯一权威 |
| "跑完了就行，不用留中间文件" | 没有中间产物，出错时无从定位在哪一步 |
| "这个失败不重要" | 静默失败是已知缺口的主要来源（PROGRESS §5 的职责） |

## Red Flags（出现即停）

- 宣布完成但 PROGRESS §4 无证据行
- 决策记录空白（放弃路线、降级选择无一行说明）
- 存在空 catch / 静默失败路径且无记录

## 验证方式

- 抽查：任取一条"完成"声明，追到 PROGRESS §4 证据，证据可复现
- 复盘测试：中断一次会话，仅凭文件能否恢复进度（新会话从 PROGRESS 续跑）
