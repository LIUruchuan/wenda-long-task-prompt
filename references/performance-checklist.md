# 性能检查表（Performance Checklist）

> references/ · 按需加载：项目有**明确规模预期**（大文件、大数据量、数万级条目、页面加载、实时交互）或用户提过"要快/流畅/轻量"时启用。
> 用法：编译时勾选"性能"领域 → 随包交付；核心红线内联 Part A §3b。

---

## 适用信号

- 输入/产物量级大（模型、数据、日志、构件数达万级）
- 有交互响应（加载、滚动、点击、渲染）的 Web/桌面产物
- 用户提过"流畅/快/轻量/别卡"
- 有网络请求、数据库查询、文件 I/O 循环

## 核心检查项

- [ ] 所有"要快/流畅"的表述都**量化为数字**（如 LCP ≤ 2.5s、万级条目加载 ≤ 3s），无数字的性能要求等于没说
- [ ] 循环/批量处理有规模上限意识：N+1 查询、逐条 I/O、全量加载进内存，在量级下是否成立
- [ ] 大文件/大数据有流式或分页处理路径，而非一次性读入
- [ ] 重复计算有缓存/记忆化；热路径不做无关工作
- [ ] Web 产物：首屏关键资源合理（体积、请求数）；长任务不阻塞主线程
- [ ] 性能取舍与验收**联动**：降级方案（如简化渲染）必须同步改写验收锚点（wenda 规划规则）

## 常见陷阱

- 用小数据测出"没问题"，真实量级下才暴露（revit 例：单墙测试不暴露多类别路径问题）
- 优化靠感觉不靠测量：先量化基线再优化
- 为了性能引入复杂度，牺牲可维护性且无收益数据
- 把性能优化放在功能正确之前（先正确、后优化，优化前后各测一次）

## 反合理化表

| 借口 | 现实 |
|---|---|
| "应该不会慢" | 无数字的"应该"无法验收，量级到了就慢 |
| "先不管性能，功能对就行" | 结构性问题（架构/算法）后期改的成本是指数级的 |
| "本地数据小，不用考虑" | 用户真实数据的量级与你测试的不同，验收必须用代表性量级 |

## Red Flags（出现即停）

- 验收标准里"流畅/快"没有数字锚点
- 有量级预期却没有任何性能验证步骤
- 出现了"数据量大就简化处理"的降级，但验收仍写"全部/完整"

## 验证方式

- 用**接近真实量级**的数据跑一遍，记录耗时/内存（时间戳或文件大小即可，不要求工具）
- 优化前后各测一次并记录差异（PROGRESS §4 证据）
- 性能指标写入 Part B 验收：数字 + 数据口径（多少条/多大文件）
