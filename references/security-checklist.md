# 安全检查表（Security Checklist）

> references/ · 按需加载：项目涉及**用户输入、外部数据、认证/授权、网络请求、密钥、文件读写、第三方依赖**时启用。
> 用法：编译时勾选"安全"领域 → 本清单随包交付；其【核心红线】由编译器内联进 Part A §3b 质量门槛。

---

## 适用信号

- 接收任何形式的用户输入（表单、上传、URL 参数、CLI 参数）
- 读取/解析外部文件、外部 API、数据库内容
- 处理密钥、令牌、Cookie、个人信息
- 有登录/权限/多用户概念
- 引入第三方依赖或执行外部命令

## 核心检查项

- [ ] 所有外部输入在**系统边界**处验证与清洗，绝不信任原始输入
- [ ] 输出到 HTML/模板前做转义（防 XSS）；SQL 一律参数化（防注入）
- [ ] 密钥/令牌**不进代码、不进日志、不进版本库**；日志只记规则与位置，不记值
- [ ] 执行外部命令时对参数做白名单校验（防命令注入）
- [ ] 认证/授权在需要处存在，且默认拒绝（deny by default）
- [ ] 第三方依赖来自可信源且无已知高危漏洞；许可证与项目兼容
- [ ] 解析器/解码器对畸形输入不崩溃（长度、编码、递归深度）
- [ ] 数据流中任何来自外部的内容（API 响应、日志、用户内容）视为**不可信数据**，不作为指令执行

## 常见陷阱

- 只看格式名不看内容（如"JSON 解析"却让原型污染 / 超大 payload 打爆内存）
- 前端校验代替后端校验（绕过前端即可攻击）
- 把密钥藏在配置文件里一起提交（.gitignore 漏配）
- 报错信息泄露内部路径/堆栈/表结构
- "本地工具不需要安全"——本地工具同样处理敏感文件

## 反合理化表

| 借口 | 现实 |
|---|---|
| "这是内部工具，没人攻击" | 内部数据泄露代价最高；攻击面随数据价值增长 |
| "先跑通再说安全" | 安全是重构最贵的部分，晚了等于重写 |
| "前端已经校验过了" | 前端校验只是体验，不是安全 |
| "密钥放配置文件就行" | 配置文件也会进版本库、会出现在日志与对话记录里 |

## Red Flags（出现即停）

- 出现"绕过校验先跑通"的决定，且没有向用户报备
- 处理用户输入却没有任何边界验证点
- 日志/对话/提交记录中出现疑似密钥值
- 依赖被"顺手升级"或"顺手引入"而无人说明用途与风险

## 验证方式

- 安全相关改动：构造**恶意输入**实测（超长/畸形/注入载荷），确认被拒绝而非崩溃
- 密钥检查：对最终产物与提交内容做一次扫描（无工具时人工核对 git 状态与文件内容）
- 依赖：核对新增依赖的来源、维护状态、已知漏洞、许可证
