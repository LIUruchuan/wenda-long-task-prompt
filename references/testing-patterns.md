# 测试模式（Testing Patterns）

> references/ · 共享清单：任何含**运行逻辑**的产物都建议启用（与"调试"领域配套）。
> 用法：编译时勾选"测试"或任一运行类领域 → 随包交付；Part A §3 测试纪律引用。

---

## 核心原则

1. **测试先于实现（TDD）**：先写会失败的测试 → 看到它失败 → 写最小实现 → 看到它通过。没看过测试失败的测试没有证明力。
2. **修 bug 先复现**：给 bug 写一个能复现它的测试（先红后绿），修复才算有证据。
3. **测行为不测实现**：断言输入→输出，不断言"调用了哪个内部方法"（实现变了测试不该崩）。
4. **金字塔**：大量小而快的单元测试、少量集成测试、极少数端到端测试（留给关键路径）。
5. **DAMP 优于 DRY**：测试要像规格说明，每条测试自包含、名字描述行为（"拒绝空标题"而非"测试1"）。
6. **一个测试一个概念**：名字里有"和"就拆。

## 常见反模式

| 反模式 | 问题 | 修正 |
|---|---|---|
| 测试实现细节 | 重构时无辜失败 | 测输入输出，不测内部调用 |
| 跳过/删除测试凑通过 | 回归无人守 | 有理由才跳，理由写 PROGRESS §3 |
| 全用 mock | 测试过、生产挂 | 真实实现 > fake > stub > mock，只在慢/不确定的边界 mock |
| 快照滥用 | 大快照无人审，一改全崩 | 少用快照，每次变更必审 |
| 测试无隔离 | 单独过、一起挂 | 每个测试自建自拆状态 |

## 反合理化表

| 借口 | 现实 |
|---|---|
| "太简单不用测" | 简单代码也会变复杂；测试就是文档 |
| "先写代码后补测试" | 后补测试测的是"做了什么"不是"该做什么"，且大概率补不上 |
| "手动测过了" | 手动测试不持久，明天的改动无从知道是否破坏 |
| "原型不用测" | 原型会变成生产代码 |

## Red Flags（出现即停）

- 实现没有对应测试 / 测试在实现之后
- 测试首次运行就通过（可能没测对东西）
- 跳过、禁用、删测试且无理由记录
- 测试名字不描述行为

## 验证方式

- 全量测试通过 + 覆盖被改动行为 + 新行为有先失败过的测试
- 每次改动后运行项目自己的测试命令（不猜默认命令）
